【实战笔记】OWASP Top 10 - SQL 注入：身份验证绕过

0. 前言

在 Web 安全领域，SQL 注入（SQLi）始终高居 OWASP Top 10 榜单。本文记录了在 PortSwigger 学院中完成的“允许登录绕过的 SQL 注入”实验过程及底层原理分析。

注：以上标签以上的文字会显示在首页摘要，点击“阅读全文”才能看到后面内容。

1. 漏洞原理简述

SQL 注入 (SQL Injection) 是由于应用程序未对用户输入的 SQL 指令进行有效过滤，导致后端数据库执行了非预期的查询。

在登录绕过场景中，后端验证逻辑通常如下：
SELECT * FROM users WHERE username = 'USER_INPUT' AND password = 'PASSWORD_INPUT'

通过构造特殊的输入，我们可以破坏原有的逻辑结构，强制使查询结果返回“真”。

2. 核心 Payload 分析

本次实验针对 username 字段使用了以下注入语句：

Payload: administrator'--

逻辑解析：

  • ' (单引号)：闭合 SQL 语句中 username 值的左半部分。
  • -- (注释符)：在 SQL 中代表单行注释，它会使数据库忽略掉后面原本用于校验密码的 AND password = '...' 部分。

实验环境：PortSwigger Academy - SQL injection vulnerability in WHERE clause allowing login bypass

1. 什么是 SQL 注入？

简单来说，SQL 注入就像是你在填表格时，在原本应该填“姓名”的地方填入了一段“后台指令”。

当服务器没有对你输入的内容进行严格检查，直接把这段指令拼接到数据库查询语句中时，数据库就会“误以为”这是开发人员让它执行的操作。通过这种方式，攻击者可以越过权限，直接读取、修改甚至删除数据库里的敏感数据。

2. 核心 Payload 分析

在登录界面，最经典的“万能密码”通常是：
' OR 1=1--

为什么它能生效？

假设后台的 SQL 查询逻辑是：
$SELECT * FROM users WHERE username = ‘admin’ AND password = ‘$password’$

当我们输入上述 Payload 后，SQL 语句变成了：
$SELECT * FROM users WHERE username = ‘admin’ AND password = ‘’ OR 1=1 –’$

  • ' (单引号)：用来闭合掉代码中原本的第一个单引号。
  • OR 1=1：由于 $1=1$ 恒等于真（True），整个 WHERE 子句的结果永远为真。
  • -- (注释符号)：这非常关键。它会把后面剩下的 SQL 代码（比如原本用来验证密码的结尾引号）全部变成注释掉，让数据库直接忽略它们。

结果：数据库不看密码，直接让你登录成功！

4. 防御建议

想要彻底杜绝 SQL 注入，靠过滤特殊字符是不够的，最标准且有效的方案是：

  • 参数化查询（Parameterized Queries / Prepared Statements）：
    它的原理是在 SQL 语句发送到数据库之前，先定义好“模板”。无论用户输入什么（哪怕是删库指令），都会被数据库严格当成“普通的字符串”处理，而不会作为代码执行。
  • 最小权限原则：
    Web 应用连接数据库的账号不应拥有 SA 或 root 权限，只给它业务所需的最小读写权限。
