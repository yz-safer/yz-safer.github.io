【实战笔记】OWASP Top 10 - SQL 注入：利用 UNION 提取跨表敏感数据

0. 前言

在掌握了确定列数和寻找文本列的技巧后，我们终于来到了 UNION 注入最具杀伤力的环节：跨表查询。通过联合查询，我们可以诱导数据库将原本不应公开的表（如用户信息表）中的内容，通过合法的页面显示出来。

本文记录了在 PortSwigger 学院中完成“从其他表中检索数据”的实战过程。

1. 漏洞原理简述

跨表提取（Retrieving Data from Other Tables） 的核心在于将原始查询的结果集与我们自定义的查询结果集合并。

在已知列数和可用文本列的前提下，我们可以构造如下逻辑：
SELECT name, description FROM products WHERE category = 'Gifts' UNION SELECT username, password FROM users

此时，数据库会将 users 表中的 username 填充到原本显示商品名称的位置，将 password 填充到显示描述的位置，从而实现敏感信息的脱库。

2. 核心 Payload 分析

本次实验的关键在于如何精准地定位目标表和目标列。

Payload 构造：

' UNION SELECT username, password FROM users--

逻辑解析：

  • UNION SELECT：发起联合查询请求。
  • username, password：这是我们想要获取的字段名。在实际渗透中，若字段名未知，通常需要查询 information_schema.columns。
  • FROM users：指定目标表名为 users。
  • --：注释掉原始查询后续的 SQL 逻辑，防止语法报错。

执行流程图解：

  1. 原始查询：SELECT A, B FROM table1
  2. 注入后：SELECT A, B FROM table1 UNION SELECT username, password FROM users
  3. 最终页面：在原本展示商品 A 的位置显示了 administrator，在展示 B 的位置显示了其明文密码。

3. 靶场复现过程

实验环境：PortSwigger Academy - SQL injection UNION attack, retrieving data from other tables

前提条件：

  • 通过测试发现列数为 2 列。
  • 确认两列均为 字符串（String） 类型。

复现步骤：

  1. 确定目标：已知目标表名为 users，目标字段为 username 和 password。
  2. 构造并发送 Payload：
    在商品分类过滤处的 URL 参数中注入：
    category=Gifts' UNION SELECT username, password FROM users--
  3. 获取数据：
    刷新页面后，观察页面渲染内容。除了正常的商品信息外，页面底部多出了所有用户的账号和密码。
  4. 完成攻击：
    找到 administrator 的对应密码，登录系统。

4. 防御建议与实战总结

防御手段

  • 预编译（Prepared Statements）：依然是金科玉律。它让攻击者无法通过单引号 ’ 闭合语句来改变 SQL 的逻辑结构。
  • 最小权限原则（PoLP）：在数据库层面，Web 应用的账号不应具备跨库查询或访问系统敏感表（如 users）的权限，除非业务绝对必要。

实战总结

在真实的渗透测试中，你可能无法预先知道表名和列名。此时你需要一套标准的“侦察流程”：

  1. 探测列数 (ORDER BY)。
  2. 探测数据类型 (UNION SELECT NULL...)。
  3. 查库名 (database(), current_database() 等)。
  4. 查表名 (利用 information_schema.tables)。
  5. 查列名 (利用 information_schema.columns)。
  6. 提取数据。

【实战笔记】OWASP Top 10 - SQL 注入：利用 UNION 寻找包含文本的列

0. 前言

在确定了原始查询的列数后，下一步是找出哪些列可以用来提取数据。由于 UNION 注入要求数据类型必须兼容，我们通常需要寻找支持 字符串（String/Text） 类型的列，以便在后续步骤中显示数据库中的敏感信息。

1. 漏洞原理简述

在执行 UNION SELECT 时，每一列的数据类型必须与原始查询对应列的类型兼容。

如果原始查询的第一列是整数（Integer），而你试图在 UNION 中注入字符串，数据库会抛出数据类型不匹配的错误。因此，我们需要通过逐列替换测试的方法，找到那个能够正常渲染字符串的“出口”。

2. 核心探测手法与 Payload 分析

假设我们已经通过 ORDER BY 确定原始查询有 3 列，接下来我们要依次测试每一列是否支持字符型数据。

测试步骤：

  1. 测试第一列：' UNION SELECT 'abc', NULL, NULL--
  2. 测试第二列：' UNION SELECT NULL, 'abc', NULL--
  3. 测试第三列：' UNION SELECT NULL, NULL, 'abc'--

逻辑解析：

  • NULL 的妙用：由于 NULL 可以转换成任何类型，它在探测时不会触发类型错误。
  • 常量字符串 'abc'：我们尝试将其中一个 NULL 替换为已知的字符串。
  • 观察响应：
    • 如果页面返回 HTTP 500 或报错，说明该列不支持字符串类型。
    • 如果页面正常渲染，并在原本显示数据的位置出现了 'abc'，说明该列可以用来提取文本数据。

3. 靶场复现过程

实验环境：PortSwigger Academy - SQL injection UNION attack, finding a column containing text

复现步骤：

  1. 确定列数：
    使用 ' ORDER BY 3-- 正常，' ORDER BY 4-- 报错，确认共有 3 列。
  2. 寻找文本列：
    • 尝试第一列：' UNION SELECT 'CoUV8K', NULL, NULL-- -> 报错 500。
    • 尝试第二列：' UNION SELECT NULL, 'CoUV8K', NULL-- -> 成功！ 页面正常显示了该随机字符串。
    • 尝试第三列：' UNION SELECT NULL, NULL, 'CoUV8K'-- -> 报错 500。
  3. 执行结果：确认第二列为文本列。在本实验中，只要在指定列位置注入实验要求的随机字符串，即可通关。

Web安全实战：DVWA文件上传漏洞绕过与冰蝎GetShell

DVWA 实验笔记：文件上传漏洞绕过与冰蝎 (Behinder) GetShell 实战

0. 前言

文件上传漏洞是 Web 安全中最直观、杀伤力最大的漏洞之一。通过上传恶意脚本（Webshell），攻击者可以直接获取服务器的控制权。本文将记录在 DVWA (Medium 级别) 环境下，利用 Burp Suite 绕过服务端 MIME 校验，并使用加密后门工具 冰蝎 (Behinder) 实现远程管理的完整过程。

声明： 本文仅供安全教育与授权渗透测试使用，请勿用于非法用途。

1. 实验环境与工具

  • 靶机环境： DVWA (Security Level: Medium)
  • 拦截代理： Burp Suite Professional
  • Webshell 生成器： 冰蝎 (Behinder) v4.0
  • 实验目标： 绕过上传限制，获取服务器 WebShell 权限。

2. 核心实战步骤

第一步：生成加密 Webshell

打开冰蝎客户端，利用其内置的“服务端生成”功能：

  1. 语言选择 PHP。
  2. 设置连接密码（默认为 rebeyond）。
  3. 生成并保存为 shell.php。

技术点： 冰蝎采用动态 AES 加密通信，相比传统的“大马”或“菜刀”，其流量特征极不明显，能有效绕过 WAF 扫描。

第二步：使用 Burp Suite 绕过 MIME 校验

在 DVWA 的 Medium 级别中，服务器会检查请求头中的 Content-Type。

  1. 开启拦截： 在 Burp Suite 中将 Intercept 设置为 on。
  2. 提交请求： 在浏览器的上传页面选择 shell.php 并点击上传。
  3. 修改报文： 在 Burp 捕获的 HTTP 请求体中找到 Content-Type 字段：
    • 原始值： Content-Type: application/octet-stream
    • 修改后： Content-Type: image/jpeg
  4. 放行： 点击 Forward 发送请求。

第三步：获取上传路径

上传成功后，页面会回显文件的存储路径：
../../hackable/uploads/shell.php successfully uploaded!

结合靶机 URL，拼凑出完整的后门地址：
http://[Target-IP]/dvwa/hackable/uploads/shell.php

第四步：冰蝎连接管理

  1. 新增连接： 在冰蝎客户端右键点击“新增”。
  2. 配置信息： * URL： 填写上一步拼凑的完整路径。
    • 传输协议： 选择生成时对应的协议
    • 脚本密码： 填写生成时设置的密码。
  3. 成功 GetShell： 双击连接。现在你可以进行文件管理、开启虚拟终端、甚至执行数据库操作。

3. 深度分析

为什么能绕过？

DVWA Medium 级别的防御逻辑仅通过校验 HTTP Header 中的 Content-Type 来判断文件合法性。由于该头部字段由客户端（浏览器/代理工具）控制，攻击者可以通过 Burp Suite 轻松将其篡改为图片类型（如 image/jpeg），从而欺骗服务器后端。

为什么选择冰蝎？

传统的 Webshell 通信（如中国菜刀）流量中包含大量的明文执行命令（如 base64_decode 等关键字），极易被流量审计设备拦截。冰蝎通过在连接阶段动态交换密钥，后续所有指令均经过 AES 加密，实现了真正的“隐身”通信。

4. 防御与加固建议

要彻底防御文件上传漏洞，应采取以下措施：

  1. 后缀名白名单： 只允许指定的扩展名（如 .jpg, .png），不要使用黑名单。
  2. 文件内容校验： 检查文件的“幻数”（Magic Bytes），验证其二进制流是否符合图片特征。
  3. 随机重命名： 上传后重命名文件（如使用 UUID），防止攻击者直接猜测路径。
  4. 目录执行权限： 将上传目录设置为不可执行脚本（例如在 Nginx 中禁止该目录解析 .php 文件）。

【实战笔记】OWASP Top 10 - SQL 注入：UNION 攻击确定列数

0. 前言

在 Web 安全实战中，联合查询注入（UNION Based SQLi）是从数据库中提取海量敏感数据的利器。本文记录了在 PortSwigger 学院完成的“SQL 注入 UNION 攻击，确定查询返回的列数”实验过程。

注：在成功利用 UNION 提取数据之前，我们必须跨越第一道障碍——确定原始查询返回的列数。

1. 漏洞原理简述

UNION 操作符 的作用是将两个或多个 SELECT 语句的结果组合成一个结果集。

要在 SQL 注入中成功执行 UNION 攻击，必须严格满足以下两个前提条件：

  1. 列数相同：注入的查询必须与原始查询返回相同数量的列。
  2. 数据类型兼容：每个对应列的数据类型必须相互兼容。

如果我们不知道原始查询有多少列，直接注入 UNION SELECT username, password FROM users 会直接触发数据库报错。因此，探测列数是 UNION 注入的必经先决步骤。

2. 核心探测手法与 Payload 分析

使用 UNION SELECT NULL 进行枚举

通过递增 NULL 值的数量，直到查询不再报错。

测试 Payload 序列：

逻辑解析：

  • 我们使用 NULL 是因为 NULL 可以被隐式转换为几乎所有常见的数据类型（如字符串、整数等），这完美避开了“数据类型必须兼容”的限制。

  • 当 NULL 的数量与原始查询的列数不匹配时，页面通常会返回错误（如 HTTP 500）或不返回任何内容。

  • 结论：当页面返回正常的 HTTP 200 响应，且不报错时，当前的 NULL 数量即为列数。

3. 靶场复现过程

实验环境：PortSwigger Academy - SQL injection UNION attacks, determining the number of columns returned by the query.

复现步骤：

  1. 截获请求：访问商店页面，点击任意分类过滤器（例如 category=Gifts），使用 Burp Suite 或浏览器开发者工具截获该 GET 请求。
  2. 利用 UNION SELECT 验证：
    • 注入 Payload：Gifts' UNION SELECT NULL, NULL, NULL--+
    • 页面正常渲染，未出现报错，进一步确认了列数为 3。
  3. 执行结果：成功确认列数，靶场挑战完成。

4. 防御建议与总结

防御 UNION 注入（以及所有类型的 SQL 注入）最有效的方法是实现参数化查询（Parameterized Queries），即通常所说的预编译语句（Prepared Statements）。

核心原理：

  • 职责分离：SQL 指令和用户数据被分开发送给数据库引擎。
  • 字面量处理：数据库引擎将输入内容严格视为“字面值”，而不是可执行代码。即使输入中包含 ' UNION SELECT...，它也只会被当作一段无害的普通字符串处理。

其他防御层：

  • 最小权限原则：确保应用程序连接数据库的账号只拥有其业务必需的表访问权限。这可以防止攻击者利用 UNION 跨表读取敏感的管理员信息。
  • 输入验证：对预期输入使用“白名单”校验（例如确保 category 参数仅包含字母和数字）。

【实战笔记】OWASP Top 10 - SQL注入基础原理与万能密码绕过

1. 什么是 SQL 注入？

简单来说，SQL 注入就像是你在填表格时，在原本应该填“姓名”的地方填入了一段“后台指令”。

当服务器没有对你输入的内容进行严格检查，直接把这段指令拼接到数据库查询语句中时，数据库就会“误以为”这是开发人员让它执行的操作。通过这种方式，攻击者可以越过权限，直接读取、修改甚至删除数据库里的敏感数据。

2. 核心 Payload 分析

在登录界面，最经典的“万能密码”通常是：
' OR 1=1--

为什么它能生效？

假设后台的 SQL 查询逻辑是：
$SELECT * FROM users WHERE username = ‘admin’ AND password = ‘$password’$

当我们输入上述 Payload 后，SQL 语句变成了：
$SELECT * FROM users WHERE username = ‘admin’ AND password = ‘’ OR 1=1 –’$

  • ' (单引号)：用来闭合掉代码中原本的第一个单引号。
  • OR 1=1：由于 $1=1$ 恒等于真（True），整个 WHERE 子句的结果永远为真。
  • -- (注释符号)：这非常关键。它会把后面剩下的 SQL 代码（比如原本用来验证密码的结尾引号）全部变成注释掉，让数据库直接忽略它们。

结果：数据库不看密码，直接让你登录成功！

4. 防御建议

想要彻底杜绝 SQL 注入，靠过滤特殊字符是不够的，最标准且有效的方案是：

  • 参数化查询（Parameterized Queries / Prepared Statements）：
    它的原理是在 SQL 语句发送到数据库之前，先定义好“模板”。无论用户输入什么（哪怕是删库指令），都会被数据库严格当成“普通的字符串”处理，而不会作为代码执行。
  • 最小权限原则：
    Web 应用连接数据库的账号不应拥有 SA 或 root 权限，只给它业务所需的最小读写权限。
